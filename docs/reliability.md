# swan_rag · 可靠性设计（Reliability Design）

> 本文档是 swan_rag 的失败模式与兜底路径说明。目标：让「知识问答服务」在真实运行中可预期、可恢复、不自欺——尤其在大模型输出不可控的前提下，通过工程手段把不确定性关进笼子。

---

## 一、可靠性设计原则

1. **LLM 是不可靠组件，工程必须兜底**：大模型可能幻觉、超时、拒答、截断。可靠性设计的核心是「默认它不可靠」，再用多层机制兜住。
2. **数据可信优先于答案漂亮**：检索不到就直说「资料不足」，不编造；引用必须可溯源。
3. **可恢复性**：任何故障都要有路径回到可用状态，而不是把错误抛给调用方。
4. **可观测性**：每个请求都有审计轨迹（QA 落库），失败可复盘。

---

## 二、失败模式清单（FMEA）

| 编号 | 失败模式 | 触发场景 | 影响 | 现有兜底 |
|---|---|---|---|---|
| F1 | **LLM 幻觉 / 答案无依据** | 检索召回不足，模型自由发挥 | 答错、误导 | 系统提示强约束「只能依据资料，不足则说明」；引用 citations 随答返回；离线评测闭环（eval_golden）把关 |
| F2 | **知识库数据陈旧（源改索引未动）** | 修改 corpus 后未重灌库 | 答旧数据（曾真实发生：43/韶关事故） | **启动自愈合**：`app/seed.py` 比对 `data/corpus/*.md` 哈希，漂移即清旧建新，从根上消除 stale 索引 |
| F3 | **错误资料写入知识库** | 人工编辑 corpus 时混入虚构内容 | 长期返回错误 | **数据接地护栏**：`store_facts.json` / `business_facts.json` 唯一真相源 + `test_grounding.py` / `test_business_grounding.py` 一致性卡点，pytest 不通过即阻断合并 |
| F4 | **LLM 超时 / 网络故障** | 上游 API 抖动、超时 | 请求失败 | 待补：统一超时 + 重试 + 降级策略（当前直接失败并返回错误信封，调用方可见） |
| F5 | **嵌入（Embedding）服务不可用** | Embedder 供应商故障 | /ingest 与 /chat 均失败 | 供应商抽象（`get_embedder()`）可切换 mock/real；离线 mock 保证开发可跑 |
| F6 | **非法请求 / 恶意调用** | 无 Key 或错误 Key | 数据暴露、资源滥用 | 全局 `X-API-Key` 鉴权，未带/错误一律 401 统一错误信封 |
| F7 | **请求参数错误** | 客户端传非法字段 | 业务不可达 | 全局 `RequestValidationError` 处理，返回 422 统一错误信封 |
| F8 | **向量索引损坏 / 数据库丢失** | 文件删除、磁盘故障 | 问答不可用 | 索引可再生产：删除 `swan_rag.db` 后启动应用即自动重建（自愈合）；db 在 `.gitignore`，不依赖提交物 |

## 三、兜底路径（按优先级）

| 层级 | 机制 | 说明 |
|---|---|---|
| **预防** | 数据接地护栏 + pytest CI | 错误资料在进入 corpus 前被拦截（F2/F3 根因消除） |
| **检测** | 启动自愈合比对哈希 | 源文件一旦漂移，启动即重建索引，不等人发现 |
| **隔离** | 全局鉴权 + 统一错误信封 | 非法请求在进入业务前被拒绝（F6/F7） |
| **审计** | QA 表落库（question/answer/citations） | 每次问答留痕，事后可复盘 Badcase 并反哺评测集 |
| **恢复** | 删库自动重建 / 供应商切换 | 索引损坏或 Embedder 故障时，恢复路径明确（F5/F8） |

## 四、长链任务状态管理（说明）

swan_rag 当前为「单轮问答 + 检索」的短链路，无跨请求长链任务，因此不涉及断点续跑/状态持久化的长链需求。若演进为多轮 Agent（如门店智能体巡检流程），可靠性设计将扩展：

- 任务状态持久化（DB 表记录任务 ID / 步骤 / 进度 / 输入输出）
- 断点续跑（失败步骤可重放，不重复已成功步骤）
- 超时治理（每步超时阈值 + 整体超时上限）
- 人机协同（关键决策节点人工确认，与 AI 自动化并行）

该设计已在 `store_tool` 的工程底座（FastAPI + SQLModel + Alembic + Docker）上具备落地条件。

## 五、与「评测闭环」的关系

可靠性不是一次性设计，而是靠**持续评测**维持：

```
golden-set（eval_golden.json）→ pytest 自动化回归 → 检索命中率阈值（≥0.75）
        ↓
Badcase 复盘 → 修正 corpus / 调整检索参数 → 回归
```

详见《效果评测报告》：`docs/eval-report.md`。
