## 三、瓶颈分析（为什么基线只有 56 QPS）

基线压测（并发 100）暴露 3 个叠加瓶颈：

### 1. SQLite 默认 rollback journal 模式：并发写串行 + fsync

`/chat` 每次请求都会把 QA 审计记录 `session.add(qa); session.commit()`。
SQLite 默认 rollback journal 模式下：

- **单写者**：所有写事务串行执行，高并发下互相排队
- **每次 commit 都 fsync**：磁盘刷盘成为隐藏延迟

300 个请求的审计写全部串行化，成为第一重锁竞争。

### 2. 聚合索引每次请求都写盘

`rag.chat()` 里 `wiki.save_index()` 每次请求都把聚合索引 JSON 写回磁盘。
高并发下多个线程同时写同一个文件，互相覆盖 + IO 竞争。

### 3. 检索数据每次请求全量重建

`retriever.search()` 每次请求都：

- `SELECT * FROM chunk` 全表扫描
- 逐条 `json.loads()` 解析向量
- 纯 Python 计算余弦相似度
- **重建整个 InvertedIndex 倒排索引**

这些工作在语料不变时结果完全相同，属于纯浪费——但在每次请求中都重复执行。

## 四、优化措施（4 项）

### 优化 1 · SQLite 开启 WAL 模式 + 并发 PRAGMA

`app/database.py` 增加连接事件，每个连接建立时设置：

```python
PRAGMA journal_mode=WAL       # 读写不互斥，写事务追加到 wal 文件
PRAGMA synchronous=NORMAL            # WAL 下崩溃不损坏库，减少 fsync
PRAGMA busy_timeout=5000             # 并发写排队而非立即报错
```

### 优化 2 · 聚合索引落盘节流（仅构建时写）

`app/wiki.py`：

- `save_index(force=False)`：默认跳过写盘
- `build_wiki(save=False)`：`/chat` 只读路径不触发落盘
- 仅当聚合层实际重建（语料哈希变化）才写盘

### 优化 3 · QA 审计落库异步批量

`app/rag.py` 新增后台审计线程：

- `/chat` 请求只把 QA 记录放入内存队列（非阻塞）
- 后台线程每 50ms 批量取出，一次事务写库
- **请求不再等待 commit**，写锁竞争大幅降低

### 优化 4 · 检索数据进程级常驻缓存

`app/retriever.py` 新增 `_CHUNK_CACHE`：

- 全量 chunk、InvertedIndex、文档标题映射常驻内存
- 以语料哈希为指纹，仅在语料变化时重建
- `get_cached_chunks()` / `get_doc_titles()` 供请求复用，避免每次全表扫描 + 重建索引

配套：`build_wiki` 的语料哈希也做 mtime 快照缓存，避免每次请求全盘扫描文件。

| 阶段 | QPS | P50 | P95 | P99 | 说明 |
|---|---|---|---|---|---|
| 基线（18:38） | 56.69 | 1130 ms | 2225 ms | 3667 ms | 原始代码，全部瓶颈叠加 |
| +WAL + 落盘节流（18:50） | 106.14 | 802 ms | 952 ms | 983 ms | 写竞争明显缓解，QPS +87% |
| +异步审计 + 检索缓存（18:58） | 183.34 | 412 ms | 560 ms | 598 ms | 吞吐再 +73%，尾延迟大幅压缩 |
| +缓存失效修复（最终） | 182.27 | 469 ms | 555 ms | 611 ms | 修复 `/ingest` 后缓存不失效，性能基本持平 |

> 18:52 曾用 httpx 连接池客户端复测，结果与标准库一致（QPS 129 / P50 690ms），
> 排除客户端瓶颈，确认优化都在服务端生效。
>
> **正确性修复说明**：检索缓存最初只跟踪 corpus 文件哈希，`/ingest` 写入的新 chunk
> 不会触发缓存失效，导致测试 `test_eval_retrieval_hits` 召回率掉到 0.25。
> 修复：指纹改为「corpus 哈希 + chunk 行数 + 最大 id」（单条 SQL），`/ingest` 后自动失效。
> 已端到端验证：灌入新文档后立即查询能命中新文档，22 个 pytest 全部通过。

## 七、经验总结（可迁移）

1. **先 profile，再优化**：cProfile 显示单请求仅 11ms，但并发压测 P50 高达 1.1s——瓶颈在高并发下的资源竞争，不在单请求逻辑。**用并发压测暴露竞争，用 profile 定位逻辑热点**，两者互补。
2. **SQLite 并发写是最大隐藏杀手**：默认 rollback journal 模式对高并发写极不友好。WAL + synchronous=NORMAL + busy_timeout 是零成本、立即生效的修复。
3. **避免「每次请求做重复工作」**：索引、向量、倒排、文档映射都是只读数据，语料不变就不该重建。**进程级缓存 + 哈希指纹** 是通用解法。
4. **同步 I/O 移出请求关键路径**：审计、日志等非关键写操作，用内存队列 + 后台批量写，能显著降低请求延迟（异步审计优化贡献了最后一档提升）。
5. **诚实标注边界**：本优化针对单机 SQLite 演示场景。生产级应换 pgvector + 连接池 + 多副本（K8s 清单已就绪，见 `docs/k8s-deploy.md`）。
