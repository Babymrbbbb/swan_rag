# 从"答错 43 家门店"到数据可信：一个 RAG 知识库的可靠性实战

> 作者视角：RAG 应用架构实践 ｜ 技术标签：FastAPI / RAG / 数据治理 / 评测闭环 / 可靠性
> 适用读者：正在做 RAG/知识库问答，并关心「数据可信」而不是「demo 能跑」的工程同学。

---

## 一、事故：知识库为什么会答错门店数？

一个品牌知识问答 RAG 服务，被问到「品牌在哪些城市有门店」时，长期返回：

> "43 家直营门店，清远 28 家，广州 9 家，佛山 4 家，**韶关 2 家**。"

问题在于：**真实门店清单里根本没有韶关**，真实分布是 47 家（清远 40 / 广州 4 / 肇庆 2 / 佛山 1）。

这个错误不是 LLM 幻觉，而是**知识库源文件从创建时就被写错了**——是当时人工编造的分布，且从未核对真实数据。更隐蔽的是：即使后来把源文件改正了，**线上检索依旧返回旧答案**。为什么？

因为 RAG 的索引是「源文件 → 灌库脚本」生成的静态产物。改源文件只是改了 `.md`，向量库里的 `document`/`chunk` 表还是旧的。**源改了，索引没动**——这是 RAG 项目最常见也最致命的坑。

---

## 二、根因拆解：不是一层问题，是四层叠加

复盘后发现，这个事故背后是四层问题同时存在：

| 层 | 问题 | 本质 |
|---|---|---|
| 内容层 | corpus 里的门店数/城市是**凭空编的**，从未 grounding 到权威数据 | 数据来源不可信 |
| 索引层 | 改源后**未重建索引**，线上查的仍是旧库 | 源与索引脱节 |
| 测试层 | pytest 把语料重灌进**临时库**，只证明"源文件对了"，生产库从未被测试覆盖 | 测试绿 ≠ 线上对 |
| 修复层 | 上次纠正只改了部分文件，**漏掉品牌概述**里的"覆盖…韶关" | 修复不完整 |

这是一个非常典型的教训：**RAG 的"答案质量"首先不是模型问题，而是数据与工程问题。**

---

## 三、解法一：单一真相源（Single Source of Truth）

第一步，把业务数据从"散落在多个 md 里"收敛为**唯一真相源**。

- 门店数据 → `data/store_facts.json`（含总数、城市分布、不存在的城市清单）
- 门店以外的业务事实（新品上市日期、加盟门槛、包材规格…）→ `data/business_facts.json`

真相源是**唯一更新入口**。任何数据变更只改这里，不再手改多个 md。

配套一个生成器：`scripts/generate_stores_md.py` 从真相源**重建**门店网络 md 文件，杜绝手写漂移。门店网络文件从此不再人工编辑。

---

## 四、解法二：启动自愈合，让索引永远跟得上源

索引 stale 的根治方案：**应用启动时比对语料哈希，漂移即重建**。

```python
# app/seed.py 核心逻辑（简化）
def reseed_if_needed(session):
    current = corpus_hash()          # 对 data/corpus/*.md 求稳定哈希
    stored  = get_meta("corpus_hash")
    doc_count = count_documents()
    if stored == current and doc_count > 0:
        return False                 # 一致，跳过
    rebuild_corpus(session)          # 清旧建新 + 写回最新哈希
    return True
```

`corpus_hash()` 对所有 md 按文件名排序后取 SHA-256，保证确定性。`Meta` 表存上一次哈希，启动时比对。

效果：**任何人改了源文件，下次启动服务就自动重建索引**，不再依赖"记得手动跑灌库脚本"。

## 五、解法三：数据接地测试，把错误卡在 CI

自愈只能保证"索引和源一致"，但**源本身如果就是错的呢**？所以还要有"接地测试"——校验 corpus 与真相源的一致性：

```python
# tests/test_grounding.py（数据无关，不写死任何数字）
def test_no_fabricated_city():
    text = corpus_text()
    for city in facts["nonexistent_cities"]:
        assert city not in text   # 真相源说"不存在"的城市，corpus 不得出现

def test_store_total_consistent():
    totals = re.findall(r"(?:拥有|全国)\s*(\d+)\s*家门店", corpus_text())
    assert totals
    assert all(int(t) == facts["total_stores"] for t in totals)
    # corpus 里所有"X 家门店"必须等于真相源总数，抓 stale/矛盾

def test_distribution_matches_truth():
    for city, n in facts["distribution"].items():
        assert city.split("（")[0] in corpus_text()
        assert str(n) in corpus_text()
```

这套测试的关键是**数据无关**：不写死 47、不写死韶关，而是动态读取真相源。因此：
- 真实数据更新（门店变 50 家、新增城市）→ 测试自然通过，不误伤；
- 漏改某个文件（还写 47 而真相源是 50）→ 测试抓出矛盾数字，阻断合并。

业务事实同样处理：`tests/test_business_grounding.py` 要求真相源里每条事实的关键词必须出现在 corpus（必现校验）。改 facts 没同步 corpus，pytest 就红。

## 六、解法四：评测闭环，让质量可回归

数据可信之后，还要证明"检索真的准"。为此建了 golden-set 评测：

- `data/eval_golden.json`：8 个覆盖核心业务场景的问题 + 期望命中文档 + 期望事实提示词
- `app/eval.py`：跑「检索命中率」（期望文档是否在 top-k 召回内）与「忠实度」（期望事实是否出现在答案或召回原文）
- 评测结果落库为 QA 审计记录，可复盘 Badcase

实际效果（离线 Mock 确定性评测）：**8/8 全命中，检索命中率 1.0，忠实度 1.0**。

评测还发现了**真实 Badcase**：问"竞品金粒门主打什么品类"，top1 召回是"品牌介绍"而非"竞品分析"。虽然 top-k 覆盖了期望文档（命中率仍 1.0），但暴露了「top1 精度可提升」——改进方向是给竞品维度加权（生产版检索排序已实现，可移植）。**能发现这种 case，正是评测闭环存在的意义。**

## 七、复盘：RAG 数据可信的 checklist

如果你的 RAG 项目踩过类似坑，逐条自查：

1. [ ] **业务数据是否可追溯到权威源？**（还是某次人工编的？）
2. [ ] **改源后是否自动重建索引？**（还是靠人记得跑脚本？）
3. [ ] **测试是否覆盖生产库？**（还是只测临时库，让生产库长期不被测？）
4. [ ] **修复是否全量？**（grep 全仓确认没有漏网文件？）
5. [ ] **是否有数据接地测试卡 CI？**（错误数据在合并前就被拦截？）
6. [ ] **是否有 golden-set 评测闭环？**（质量可回归，改坏了能发现？）

---

## 八、关键收获

1. **RAG 的答案质量，首先取决于数据链路，而不是模型**。把"语料→索引→检索→生成"每一环都变成可验证的，比调 prompt 更重要。
2. **单一真相源 + 生成器 + 数据无关测试**，是一套可长期演进的数据治理模式：真实数据更新不误伤，漏改文件被自动抓出。
3. **启动自愈合**是消除"源-索引脱节"的可靠手段，成本极低（一次哈希比对）。
4. **评测闭环的价值在 Badcase**——指标达标不等于没问题，持续复盘才能让系统进化。
